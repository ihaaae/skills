# 各模块怎么写

## 定位
两三句话，回答"学它有什么用"：这一节服务哪个目标，是通往目标那条路线上的哪一环。context 里有目标和路线时按它讲，但**写成人话**：目标写它要回答的问题，路线上每一环写主题名，不写编号，学习者不记得 C10、G1 指什么；再用一句话解释这一环为什么必要。有全景图时，指出本节在图上的哪一块。不讲新知识，不出题。

原因：一连串小而扎实的 bottom-up 课会让学习者看不见自己在往哪走，学习变得没有意义感、难以坚持。定位只花半分钟，却让每节课都挂在学习者在乎的目标上。

## 知识
只讲这一层需要的原理。控制信息密度：后面几层才用得到的机制和细节，留到那一层之前再讲。

客观知识只有"是什么"是不够的，就像学一个公式，除了会算，还要知道它的几何意义、它当年解决了什么问题。所以知识模块按下面的顺序组织，能有的都要有，没有的不硬凑：

1. **动机**：先用一两句说它要解决什么问题，或者是什么约束逼出了这个设计（历史场景也算）。例如"CAN 最早用在车里，没有 host 统一调度谁说话 → 只能 broadcast，抢线时靠 arbitration"。先有问题，答案才有意义。
2. **主张**：核心原理本身。措辞要和事实一样宽："只能""没有""都""从不"这类全称说法，只在确实没有例外时用；拿不准就写清范围（"除 PDO 外都能用"，而不是"只能走 SDO"）。全称说法一旦被后文的例外推翻，学习者会以为前后矛盾。主张要逐条回应动机里提出的问题：动机列了几个代价或约束，就说清每个代价来自哪个原因，主张里哪一条针对哪一个。连接词（"可是""所以""而且"）要和实际的逻辑关系一致。否则动机和主张各写各的，读者看不出设计为什么是这样。
3. **图或表（必需）**：每个知识点至少一张。形式按内容选：机制用流程或时序图，区分用对比表，分层用层次图，全景用地图。图表要和文字讲同一件事，不放装饰图。
   - **格式**：用 mermaid 或 Markdown 表格，不画 ASCII 图。时序和消息往来用 `sequenceDiagram`，状态切换用 `stateDiagram-v2`，流程、分层、全景用 `flowchart`，区分用表格。mermaid 表达不了时（如按真实时间比例画的时间轴）再考虑 HTML。
   - 原因：ASCII 图靠等宽对齐，中英文混排时字宽不一，箭头和竖线会错位，难读。
4. **联系**（有就写）：学习者已懂的其他领域里的同类结构（如 OSI 分层、软件里的类比、学习者学过的其他知识点），一句话点出相同点和不同点。

动机和图表同样只能使用学习者已掌握的概念和本知识点已经讲过的内容，并且要被题目考到（见 questions.md 的"动机题"）。联系可以写在这里，也可以放到最后的延伸里：写在这里的联系，题目可以考；放进延伸的不考。

**知识可以分层讲。**一个知识点的内容不必在第一轮讲完。第一层的知识只讲最核心、最干净的那部分，够第一层的例子和题目用就行。后面某一层要用到新的机制或细节时，在那一层的例子之前加一段知识，标题写成 `### 知识二：<这一段讲什么>`、`### 知识三：<……>`，编号跟随层。某一层也可以不加新知识，只靠例子多加一个现实变量。判断标准是：学习者在这一轮需要读懂什么，就讲什么。分层省下来的是后面几层才用到的机制细节；第一层的动机和图表不能省，学习者要先知道这个知识点解决什么问题、为什么这样设计。原因：把一个知识点的全部机制塞进第一轮，读者要一次消化五六条主张，而题目要到很后面才考到它们。

后面几层的知识模块不必再写动机、图表、联系全套，只写这一段新内容，需要时配一张图。它和第一层的知识一样遵守主张的措辞要求，也同样要被这一层的题目考到。

## 例子
给出一个完整、具体、最简单的示例。示例是必需的，不能省略。

**例子写成"题目 + 解答"。**例子先用一两句写出一个明确的问题，形式与后面要出的题相同（"要读 9 号 drive 的 X，地址是什么？"），然后按步骤解。不要只摆出事实和推理：学习者看不出这套方法是用来回答哪一类问题的。解答**按题目的小问逐条作答**：每一问先给答案，再给理由；机制的推演放在理由里，不要先讲一遍完整过程、把答案顺带埋在里面——那样题目成了副产品，读者看不出哪句在回答哪一问。题目本身也要只问方法要回答的事，小问不超过两三个。

**一个例子配两道题，例子要示范的是解题方法。**例子不只演示结论，还要把推理轨迹摊开，给出一条可以照着走的思路：先看什么、依据哪条规律、按什么顺序排除、哪个信号最关键。最好在例子末尾把这条思路压成一两句可复用的"判断方法"（例如"先看它做什么，确定候选层；再看耗时能否保证"）。紧随其后的两道题都应当能**照这条思路一步步解出来**；问题解答也沿用同样的步骤，学习者答错时就能指出是"思路的第几步偏了"。原因：学习者真正带走的是方法，不是某个例子的答案。例子如果只给结论，题目就只能靠记忆或直觉作答，答对了也测不出方法有没有学会。出完题后自查：只看例子里的推理步骤、不看它的结论，能不能解出这两道题？解不出来，说明例子和题目脱节，要么在例子里补上缺失的推理步骤，要么改题。

例子标题与例子正文必须采用不同的语言层级：

1. 标题负责"给概念命名"：比正文更术语化，像教材里的小节标题，准确命名本层的机制、关系或场景类型。
2. 正文负责"让学习者听懂"：尽量低术语、具体、自然。必要术语第一次出现时，用简单语言解释。
3. 不要用纯生活化事件作为例子标题。例如，不要写"### 例子二：家里有人突然看视频"，更适合写"### 例子二：拥塞与延迟敏感的带宽竞争"；但正文仍然可以写"你正在下载种子，家里另一台设备突然开始看视频"。
4. 标题里不出现正文还没解释过的说法，更不能用临时造的词（如"类 PDO"）当标题：读者在标题上就卡住了，正文又没回头解释。需要一个新说法时，先在正文里用完整的句子说清它指什么、为什么这么叫，或者干脆换成已经讲过的词（不造词，用领域的标准术语）。
5. 不要为了显得专业而在标题中堆砌与当前层无关、学习者尚未接触或并不准确的术语。
6. 标题的术语化程度应随教学层级适度提高，但必须保持准确、简洁、可读。

例如，在讲 qBittorrent 的 BT 与 µTP 时，标题可以类似：
- “### 例子一：同一种子内的异构 Peer 连接”
- “### 例子二：拥塞与延迟敏感的带宽竞争”
- “### 例子三：多 Peer 并发下的传输协议混用”

## 问题
每道题都与本层的例子同构：考同一个原理，推理路径基本一致，只替换人物、数字、方向、对象、名称或少量局部条件。不加入新概念、额外变量或干扰项；这些只能在下一层先讲清、先用例子示范，再考。默认写成选择题（见 questions.md）。

## 之后的每一层
每一层在前一层的基础上前进一步：

- 第一层：最简单、最干净的模型，只保留核心机制；
- 中间的层：每层加入一个主要的现实变量，或者一段新的机制（用知识N 先讲清），让场景更接近真实情况；
- 最后一层：较完整、较真实的场景，可以包含多个因素、少量干扰信息或需要综合判断的条件，但仍然建立在前面各层之上。

## 延伸：<讲什么>（可省略）
全部题目做完后，可以再讲一段不考的内容：和其他领域的联系、从另一个视角看这个知识点、它的来龙去脉、现实中的变体。它的作用是把这个知识点和学习者已有的知识连起来，所以不出题，后续课程和题目也不依赖它。开头用一句话说明"这一段不考"，篇幅控制在一两段，加一张图或表。延伸同样只用学习者已掌握的概念和本知识点讲过的内容。没有值得讲的就省略。

## 回到全景
用三四句话收尾，这是本节的 top-down 部分：
- 用一句话总结学习者已掌握的核心规律；
- 回到"定位"里的那张图或那条路线：这节课补上了图上的哪一块，学习者现在能回答哪个以前答不了的问题；
- 下一环会补上什么（一句预告，不展开讲）；
- 如有必要，指出现实中的例外或边界条件。

不出题。它的作用是把刚学的细节挂回整体，不是再教一遍。
