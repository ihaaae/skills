# Topic Graph

Teaching a hard subject to someone without the background fails in three predictable ways: explanations quietly lean on concepts the learner doesn't have yet; lessons are too large for anyone to tell whether they landed; and across sessions, nobody remembers what was actually verified versus merely said. A topic graph fixes all three. A fourth failure comes from fixing the first three too well: a long run of small, verified, bottom-up nodes leaves the learner unable to say what any of it is for or where it sits, and motivation drains away. The graph guards against that too (see "Big picture and meaning"). The subject is cut into small nodes, each node lists the nodes it depends on, and the files record which nodes the learner has *demonstrably* mastered. Those files are the only memory that survives between sessions, so most of this skill is about keeping them trustworthy.

**Facts vs. derived state.** Only two things are hand-maintained: each node's prerequisites and each node's mastery status. Everything else — 🔓/🔒, the frontier, which 📝 nodes can be retested, what to learn next, the overview diagram — is *computed* by `scripts/graph.py`. Never hand-edit derived state, and never trust a recollection over the script.

## How this fits with progressive-learning

- **topic-graph** decides *what* to learn and *in what order*: building and growing the graph, diagnosing prior knowledge, picking the next node, policing which concepts may be referenced, and persisting progress.
- **progressive-learning** decides *how* to teach a single node: 定位 → 知识 → 例子 → 同构问题 → 解答 → 复测 → 升级 → 回到全景, in explicit modules.

A node is sized so that one complete progressive-learning run fits in it. A session is: `next` → `preflight` → teach with progressive-learning → write the summary and `set` the status → repeat or stop.

Prerequisite diagnosis lives here, not in progressive-learning, because "what does the learner already know" is exactly the question the graph answers.

## Topic directory layout

A topic is a directory containing `topic.yaml`. Everything below is relative to it.

```
topic.yaml            config: title, main track groups, goals (targets + question), optional rhythm
goals.md              goals, non-goals, route intent (preferences the script can't encode)
rules.md              domain rules specific to this topic (generic rules live in this skill)
nodes/<G>/_group.md   group title (YAML front matter) + group-level notes (simplifications, previews)
nodes/<G>/<ID>.md     one node: YAML front matter + summary body
glossary.md           terms, Chinese ↔ standard English
open-questions.md     unresolved facts and competing explanations, with self-tests
debts.md              open items only: forward references, misconceptions awaiting retest, flawed exercises,
                      deferred re-checks; delete an item once paid
sources.md            references: one line per source, with credibility and the nodes it serves
references/           saved teaching texts (tutorials, chapters, clippings), kept verbatim — see below
material/             optional: the object of study itself (a repo, a book), read-only
retro.md              outer-loop log: one `## YYYY-MM-DD` entry per retrospective (section I); newest date = last retro
STATE.md              GENERATED by `graph.py sync` — never hand-edit
log.jsonl             GENERATED by `graph.py set` — machine log of status changes
archive/              retired documents, kept for reference
```

A node file:

```
---
id: "T6"
title: "hop < 帧长 ⇒ STFT 是过完备/冗余表示"
prereqs: ["T4", "D7"]
targets: []               # optional, see Edges
status: "mastered"        # new | taught | mastered | retired
caveat: ""                # optional: scope in which a ✅ still holds
updated: 2026-09-29
verified: 2026-09-29      # written by `set … mastered`; drives review (section J)
mode: ""                  # optional: "reading" for a reading node (see Nodes)
---
Body: the summary of what was actually taught (see "Writing node summaries").
```

Splitting into files is what makes context cheap: a session loads `rules.md`, `STATE.md`, and — via `preflight` — only the node being taught plus its prerequisites' summaries, not the whole graph.

Optional rhythm settings in `topic.yaml` (defaults shown):

```yaml
rhythm:
  review_after_days: 14     # a ✅ older than this, with dependents, is offered for review
  retro_gap_days: 7         # suggest a retro after this long without a status change
  retro_every_changes: 12   # …or after this many status changes since the last retro
```

### Reference texts

An agent writing a lesson from scratch often produces a flatter explanation than a good human-written tutorial: it has less history, fewer well-chosen pictures, and less sense of what matters first. So a topic may keep such texts in `references/` (one subdirectory per publisher or series is fine). They are saved verbatim, every one gets an entry in `sources.md` with its credibility, and the learner may add more at any time.

How they are used:
- **When drafting a node (D.2), read the matching sections first.** Borrow their structure, motivation, history and pictures, and say in your own words what they say; don't paste long passages. Facts are still checked against the authoritative source the reference rests on (a standard, the official docs). A vendor tutorial is good at explaining and weak as an authority.
- **Reading nodes assign sections from here.** The learner reads the original text, not a summary of it.
- **Record conflicts.** When a reference contradicts an authority or another reference, the conflict goes in `open-questions.md`.
- **They are not the study object.** `material/` holds the thing being studied; `references/` holds texts that help explain it. The "learner doesn't read the material" rule never covers `references/`, and the learner can read them freely.

## Where things live

Rules and preferences pile up from many corrections. Put each in exactly one place, or the copies drift apart and contradict each other. Decide by scope:

| Scope | Place | Examples |
|---|---|---|
| How to teach and track *any* subject, for *any* learner | this skill and progressive-learning | explain only with ✅ concepts; map/synthesis nodes; motivation + picture; retro and review |
| One learner, *every* topic in a workspace | the workspace's `AGENTS.md` (e.g. `Learn/AGENTS.md`) | teaching language and term style; how this learner likes questions; workspace layout and tooling; the session routine |
| One topic | the topic's `rules.md` (domain rules), `goals.md` (goal, altitude, non-goals, route), `topic.yaml` | altitude ("architect: test design consequences"); domain anchors and source quirks |
| How to enter a topic | the topic's own `AGENTS.md`, a few lines | what the material is, where it lives, that it is read-only |
| Not yet sure where it belongs | auto-memory | a fresh correction, until a retro promotes it |

Auto-memory is keyed to the directory a session runs in, so a preference saved while working in one topic is invisible from another. Anything meant for every topic must go into the workspace `AGENTS.md` or a skill. A memory that has been promoted is deleted, so that no second copy exists. Rule numbers in `rules.md` are referenced from other files, so they are never renumbered: a rule that moves to a skill keeps its number and becomes a one-line pointer.

## The script

Run from anywhere inside the topic directory (or pass `--root`). The script declares its dependency (pyyaml) inline per PEP 723, so `uv` prepares the environment automatically; no manual install.

```
uv run <skill-dir>/scripts/graph.py <command>
```

In the `Learn/` workspace, `mise run graph <command>` does the same from the current directory. Tests: `mise run test`.

| Command | Use |
|---|---|
| `check` | Validate: unknown/retired prereqs, cycles, duplicate IDs, a ✅ whose prereqs aren't all ✅, ✅/📝 nodes with no summary, unrecorded forward references. Exit 1 on errors. |
| `next [-n N] [--json]` | Compute what to learn next (ranking below), and for the top pick, the chain of nodes leading from it to each goal it serves. Above it, any reasons to hold a retro first (section I); below it, the ✅ node most due for review (section J). |
| `preflight ID` | Refuses a node whose prereqs aren't all ✅. Otherwise prints the route from this node to each goal it serves (plus the goal's `question`, if set), the permitted concepts, caveated ✅ nodes, direct prereqs' summaries, and the node's existing body. |
| `show ID` | Node, its status, prereqs, dependents. |
| `set ID mastered\|taught\|new [--caveat "…"]` | Record status. `mastered` also stamps `verified` with today's date. Refuses `mastered` if prereqs aren't ✅; warns when demoting a node that ✅ descendants rely on. |
| `add ID --title T --prereq A,B [--target X] [--group-title G]` | Create a node (rolls back if it breaks the graph). |
| `retire ID --into ID2` | Retire a node; the ID is never reused. |
| `sync` | `check`, then regenerate `STATE.md` (overview, progress toward goals, next step, all nodes). |

### How `next` chooses

The ranking is lexicographic, so it is explainable:

1. **📝 nodes whose prereqs are all ✅** (retest due) come first — retests are cheap while content is fresh and each one unlocks a subtree.
2. **Main-track groups** (`[track] main` in `topic.yaml`) before side groups.
3. **On a goal path** (an ancestor of a `[[goal]]` target, or the target itself) before off-path.
4. **Bottleneck**: more transitive dependents first.
5. Track order, then ID.

It also names one side-group node as a "change of pace". The output is a *recommendation with reasons*; the learner picks. If the learner's real problem points elsewhere (section E), that overrides the ranking — but only among nodes the script says are teachable.

## Nodes

### What a node is

A node is one claim, one distinction, or one mechanism that the learner could state in a sentence once they understand it. Good node titles read like the thing to be understood, not a chapter heading: "Vocal fold tension → pitch" rather than "Pitch"; "Connection direction ≠ data direction" rather than "TCP basics". A node whose whole point is the relationship between two things ("independently controllable, but coupled in effect") is still one node.

### Map, mechanism and synthesis nodes

A graph built only by chaining backward is purely bottom-up: every node is a detail, and the learner meets the whole only at the very end, if at all. Good learning alternates — see the whole roughly, go down into one part, come back up and see the whole more sharply. Build that rhythm into the graph with three kinds of node:

- **Map node** (top-down, at the entry of a group or a big subtree): "X consists of these parts; each part answers this question." Example: "CANopen = object dictionary + communication objects + device states + device profiles; each answers one question about a device." Teach it early, roughly, as a scaffold, and mark it a prerequisite of the group's first detail nodes. Test it by classification ("a new requirement appears — which part handles it?"), never by the parts' details. Every later detail lesson points back to its place on this map.
- **Mechanism / claim node** (bottom-up, the default): one claim, one distinction, one mechanism, as described above.
- **Synthesis node** (top-down again, after several details): one cross-cutting idea that only becomes visible once the parts are known — a comparison table across them, a classification, a design trade-off. Example: "the communication objects fall into three interaction models: master/slave, client/server, producer/consumer". Its prereqs are the details it unifies. Test it by applying the classification to a case not taught before.

Each main-track group should have a map node near its entry and at least one synthesis node near its end. A group's `_group.md` carries the map as a picture or table, with each part linked to the node that teaches it, so the learner can always see where they are.

### Reading nodes

Usually the tutor teaches and the learner never reads the source. But a well-written outside text — a good tutorial, a book chapter — can give a top-down view faster than lessons can, and a learner who chooses to read it should get credit for doing so. A **reading node** (`mode: "reading"`) assigns a short reading: which document, which sections, roughly 10–15 minutes, plus two or three guiding questions to read with. The flow:

1. The tutor gives the 定位, the reading assignment and the guiding questions, then stops.
2. The learner reads, then comes back with questions. The tutor answers them only with ✅ concepts plus what the assigned sections say.
3. Two verification questions follow, about the claims the node lists. Correct answers → `mastered`.

The node body lists the exact sections assigned and the claims they are meant to establish. Questions may rely only on those claims and never on other details of the text. Reading suits map nodes and motivation/history best. A mechanism that needs worked examples is still taught.

### The 20-minute rule

Each node, including its exercises, should take under 20 minutes: roughly one knowledge section, three examples of rising difficulty, and six short questions. Size nodes by these tests:

- **One-paragraph test.** The 知识 section can be written in a short paragraph that introduces no new term besides the node's own subject. If it needs a second new term, that term is probably its own node.
- **Ladder test.** Layer 2 of progressive-learning adds exactly one real-world variable, and that variable is already known to the learner. If layer 2 or 3 would need a concept that isn't ✅ yet, the concept becomes a separate node and this node gets smaller.
- **Question test.** You can write two isomorphic questions whose answers depend only on this node plus ✅ nodes. If you can't, the node is either too vague (sharpen the claim) or too thin (merge it into a neighbor, or make it a note on one). And every core claim of the node is hit directly by at least one question. A claim that appears only in an example was never tested, and a ✅ built on it is hollow. If six questions can't cover the claims, split the node.
- **Failure-point test.** If an exercise has two independent reasoning steps that could each fail for different reasons, that is two nodes.

Err on the side of smaller. A node that turns out trivial costs five minutes; a node that is secretly three nodes produces a lesson where the learner answers correctly for the wrong reason and nobody notices.

### IDs, groups, and edges

Each node has a short ID: a group letter plus a number (A1, S12, T23); the group letter must match the directory. IDs never change once assigned, because other sessions and the learner's own notes refer to them; a retired node keeps its file with `status: "retired"` and `merged_into`, and its ID is never reused. Groups are branches of the subject (foundations, one subsystem per letter, practice techniques, …).

Edges have a type:

- **Prerequisite** (`prereqs`, gating): to understand this node, the learner must first master that one. Only these gate unlocking.
- **Target** (`targets`, non-gating, optional): for *practice* nodes — exercises, drills, techniques — says which concept node the practice trains or exposes. Practice commonly precedes understanding, so a practice node may be learned while its target is still locked. When teaching it, you still may not *explain* using the locked target's content.

If the subject has both a "how it works" side and a "what to do about it" side, keep them in separate groups. Conclusions from practice ("this drill helps") must not be written into mechanism nodes as if they were mechanisms; observations from practice may serve as evidence for or against a mechanism.

### Statuses

Stored (`status`): `new`, `taught`, `mastered`, `retired`. Derived: 🔓 = `new` with every prereq mastered; 🔒 = `new` with some prereq not mastered.

| Mark | Meaning | Satisfies prerequisites? |
|---|---|---|
| ✅ `mastered` | Verified by diagnosis or by passing progressive-learning's retests | Yes |
| ✅ ⚠️ | `mastered` with a `caveat` (scope limit) | Yes, within the caveat |
| 📝 `taught` | Delivered but not verified (discussed, or the session ended before retest) | **No** |
| 🔓 | Unlockable | — |
| 🔒 | Locked | — |

📝 exists because content often gets delivered faster than it gets verified. It is honest bookkeeping, not a failure, but a 📝 node unlocks nothing until it is retested.

## Big picture and meaning

Verified bottom-up knowledge is necessary but not sufficient. A learner who can only recite a formula and compute with it has not understood it until they also know what problem it solved, what it looks like, and what it is for. Without that, the learning feels meaningless and stalls. Three duties follow.

**1. Every lesson knows what it is for.**
- In `topic.yaml`, each `[[goal]]` carries a `question`: one concrete question, in the learner's own terms, that they will be able to answer at the end. `preflight` and `next` print the chain from the current node to that goal's target, together with this question.
- Each lesson opens by saying, in two or three sentences, which goal it serves and which link of that chain it is. It closes by saying what the learner can now do or answer that they couldn't before, and what the next link will add.
- A node that sits on no goal path must be justified by the learner's choice (a change of pace, curiosity). Otherwise don't recommend it.

**2. Every node gets more than one angle, not just the bare claim.** Objective knowledge needs interpretation to stick. When a node is written and taught, look for these angles:
- **Motivation / history.** What problem forced this design, or what constraint makes it so? Example: CAN was born in cars with no host computer, so nobody could assign who talks — hence broadcast and arbitration.
- **Picture.** Geometric meaning, a timeline, a layered diagram, a comparison table. Every node has at least one picture or table; its form fits the node — a flow or timeline for a mechanism, a comparison table for a distinction, a layered map for a map node.
- **Connection.** The same idea in a field the learner already knows: OSI layers, an analogy from software, an earlier ✅ node in another group.
- **Consequence.** What follows for the learner's purpose (for a design-altitude learner: what it constrains in the design).

Not every angle exists for every node; don't invent history or force an analogy. These angles are explanation, not decoration, so they obey rule 2 (✅ concepts only) and get tested. The cheapest test of motivation is counterfactual: "if constraint X didn't exist, which part of the design could change?"

**3. Zoom out regularly.** The map and synthesis nodes above do this structurally. In addition:
- When the learner returns after a break, starts a new group, or seems to be losing the thread, open with a one-minute "you are here" view: the group map with ✅ parts marked.
- After a group's last node, revisit the goal's `question` and answer as much of it as the ✅ nodes allow. This shows progress in terms the learner cares about, not in node counts.

## Core rules

These apply to every topic. A topic's `rules.md` adds domain rules; those take precedence.

1. **Recommend only from the frontier.** "What next" means a 🔓 node or a 📝 node due for retest — i.e. what `next` returns — never a node with an unmastered prerequisite.
2. **Explain only with ✅ concepts.** If an explanation genuinely needs a concept from a node that isn't ✅, stop and say "this needs X first" rather than slipping it in. Slipped-in concepts are how the graph silently rots: the learner appears to follow, nobody tested the dependency, and later lessons build on it.
3. **Exercises and examples obey rule 2 too.** Before posing a diagnostic, practice or retest question, trace its correct answer and check every concept on that path. Examples are held to the same rule: a device type or domain term an example leans on is either tied to a ✅ concept or defined in one plain sentence on first use. A lookup fact the question needs but doesn't test (a standard number, a code value, a vendor's meaning for a field) goes into the stem, so the question tests the reasoning step only.
4. **Use the field's established terms; don't coin names.** If no standard term seems to exist, first suspect the distinction itself — maybe it isn't real — and research before inventing. A coined name that survives is marked as a mnemonic in the glossary, next to the standard term.
5. **Precisely defined concepts are always used with their full definition.** Examples must match the definition, not a nearby approximation.
6. **Mark attribution boundaries.** A simplified teaching model must not claim to be the *whole* cause of a phenomenon when other causal paths exist, even if those are still locked. Say "this is one path; another (node X, not yet learned) also produces this."
7. **✅ can be relied on without re-teaching.** Don't re-teach it unless it is caveated or the learner stumbles on it.
8. **Separate mechanism from statistics.** A statement about how the system works holds regardless of who is involved. A measurement of a population, and advice derived from it, must name the population — and if the learner's context differs, say so.
9. **Reconcile outside instructions before judging them.** Learners bring in cues from teachers, books, videos, and other tools. When one conflicts with the model or another cue, first ask whether they govern different axes, phases, or conditions before concluding either is wrong.
10. **The learner doesn't read the source material** unless a reading node assigned it. Every fact an answer depends on must have been taught, or be given in the stem.
11. **Define notation before using it.** A learner fluent in the underlying ideas may still not read the field's symbols (see section C). The first time a symbol appears, in a lesson or a question, define it with a small concrete example, or say it in words and numbers.
12. **Don't trust hand memory over the script.** If your recollection of a status or the frontier disagrees with `graph.py`, the script (and the files behind it) wins; fix the files.

## Workflow

### A. Starting fresh: build the graph

1. **Pin the goal.** What concept or ability does the learner want, and why? The "why" decides priorities later. Ask about background only as far as it helps you choose where to start diagnosing — self-reports don't set statuses. Write `goals.md`, including explicit non-goals.

   **Pin the altitude too, before chaining backward.** "Understand X" can mean implement it, review someone else's work on it, or oversee it (follow progress, judge risks, set plans) — and the three produce graphs of very different depth. Topic names and scope checklists don't reveal which one the learner means. Take one or two real sentences from the learning material and ask what the learner should be able to do with them at the end: re-derive them, check them, or explain what they mean for the plan. A graph built at the wrong altitude has to be rebuilt (section H).

   **Pin the object, not only the altitude.** When the learning material is a concrete thing — a repository, a project, a product — it contains two kinds of content: knowledge that exists independently of it (standards, protocols, mechanisms, common practice in the field, the hardware's own documentation), and the material's own decisions (its plans, task breakdowns, internal layering, process). Default priorities:
   - **Durable before transient.** Teach the independent knowledge; use the material's own decisions only as one-line examples of it. A project still in flux will change its plans, and a lesson built on them expires with them.
   - **General before specific.** Within durable knowledge, concepts that apply everywhere (the bus, the OS, the field's standard architecture) come before "how this device / this vendor does it".
   - **Process is a non-goal by default.** What counts as sufficient verification, how to grade evidence, when a task is "done", how to track progress — leave these out unless the learner explicitly asks to learn them. State honestly where a fact comes from, but don't turn that into a lesson.
   - **Warning sign:** node titles that mostly cite the material's own file names, task numbers or layer names mean the graph is studying the material, not the knowledge behind it. Check with the learner before building further.

   When the material's own design is unstable and the vendor's is opaque, the field's mainstream practice (widely used open-source frameworks, standards) is usually the best anchor for "architecture" topics.
   Write each goal's `question` in `topic.yaml` (see "Big picture and meaning"): one concrete question the learner wants to be able to answer.
2. **Chain backward.** From the goal, ask "what must be understood before this?" repeatedly until you reach things a general adult already knows or that you'll diagnose. Apply the 20-minute tests as you go. Then check the shape: each main group needs a map node near its entry and at least one synthesis node near its end.
3. **Create the directory**: `topic.yaml` (title, `[track] main`, one `[[goal]]` per goal with `targets` — the end-point nodes whose ancestors form the goal path), `rules.md`, and nodes via `graph.py add` (first `add` in a new group needs `--group-title`).
4. **Don't build the whole domain.** Build solidly two or three layers ahead of the frontier and leave distant regions as a few coarse 🔒 stubs. The graph grows as learning reveals what's needed.
5. **Diagnose** (section C) and `set` initial statuses.
6. Run `sync`, show the learner the frontier and recommend a first node.

### B. Starting a session in an existing topic

1. Read `rules.md` (domain rules override the defaults) and `goals.md`.
2. Run `graph.py check`. Fix errors before recommending anything.
3. Run `graph.py next` (or read `STATE.md`). If it suggests a retro, offer that first (section I); the learner may postpone it. Otherwise offer a short recommendation with the reason, including the route to the goal, and let the learner pick. Also skim `debts.md` for items the chosen node is supposed to settle, including misconceptions to retest.
4. If `next` names a node due for review, open the lesson with one review question on it (section J).

### C. Diagnosis

Diagnosis answers "which nodes can be marked ✅ without teaching?" It runs when building a new graph, when the learner wants to test out of a 🔓 node, and when a caveated ✅ node is about to be relied on.

**What counts as diagnosis.** Distinguish *environment facts* from *knowledge*. Device models, software settings, whether a symptom occurs, what the learner's teacher said — these clarify the situation but verify nothing. A diagnostic question must actually test understanding or reasoning.

**Questions must not depend on unverified terms or notation.** Don't test NAT by first asking the learner to identify WAN, private address ranges, or CGNAT; if they might not know those words, test the underlying understanding through a small concrete scenario. Notation is the same trap in another form: block matrices, `Rz(θ)`, subscripted frames, `e^{…}` — a learner fluent in the underlying math may still not read the field's symbols, and a self-reported background says which concepts may be familiar, not which symbols are. Define each symbol with a small numeric example the first time it appears, or ask in plain words and numbers. A failure caused by unreadable notation tests nothing and is voided like any flawed question.

**Prefer these forms:** predict what happens in a simple scenario; predict how a quantity or state changes; explain a reason in one sentence; choose between two very close options and say why. "Do you know X?" is not diagnosis — self-assessment can be a hint, never a verdict.

**Keep it light.** One or two high-information questions at a time; let the answers decide what to ask next.

**Don't leak.** Never state the rule you're about to test before asking.

**Stop re-testing what's been shown.** If the learner has just explained something accurately, move on to what's actually missing.

**Graph-native strategy.**

- Start from the parents of the nodes nearest the goal, not from the roots. Usually two to four prerequisites really matter; test those.
- Probe a mid-depth node first. A clean, well-reasoned pass is evidence for the ancestors its answer path used — mark those ✅ too, but only the ancestors genuinely exercised. A failure sends you down to its parents. (Mark ancestors before descendants: `set` refuses a ✅ whose prereqs aren't ✅.)
- A single correct answer can be luck. For nodes that will carry heavy weight, ask a second isomorphic question before marking ✅.
- **Gaps become nodes, not inline patches.** A missing prerequisite gets its own node (`graph.py add`) and is taught through progressive-learning — not squeezed into a two-sentence aside. Inline patches are untested dependencies.
- **A diagnostic question that turns out flawed** (it presupposed a concept or a paper's conclusion, or had two right answers) is voided: record it in `debts.md` and count it toward no node.

### D. Teaching a node

1. **Choose** with `graph.py next`. The ranking encodes the priorities: retests, then main-track bottlenecks on the goal path, then side nodes for a change of pace.
2. **Pre-flight**: `graph.py preflight ID`. It refuses locked nodes. Its output is the *allowed vocabulary* for the explanation, all three examples, and every expected answer path. If a planned example needs anything outside it, either teach that node first or cut the example down. Before teaching, fill the node's body with a draft (the claims to teach, the motivation, the planned picture or table, the source anchors) and check every claim against the source. If `references/` has a text covering the node, read it first and borrow its framing (see Reference texts). Untaught nodes often have only a title. Titles are written while the graph is built, from a quicker read, and can over-claim. If the source says otherwise, correct the title first — the learner is about to be tested on it.
3. **Teach with progressive-learning.** The node is the unit — one full run, three layers unless the node is thin enough for fewer. Teach consistently with the prereq summaries `preflight` printed. Open with the route `preflight` printed (what this node is for), and prepare the motivation and the picture or table before the lesson (see "Big picture and meaning").
4. **Mid-lesson gaps.** If the learner's question or a needed step reaches outside ✅ territory, stop and say what node it belongs to. If none exists, `graph.py add` it. Then either switch to it (and return) or mark the boundary explicitly and continue, recording a debt.
5. **Record.** Write the node's summary into its file (below), then `graph.py set`. Every layer's two questions correct → `mastered`. Session ended mid-node, or content delivered without retest → `taught`, with a note in the body of where it stopped. A wrong second retest means not mastered, regardless of the first answer.

### E. Questions from outside the graph

Learners arrive with real problems, instructions from a teacher, claims they read. These show which parts of the graph matter, but they tempt you to answer with everything you know.

- **Locate it.** Which node(s) would answer it? If locked, say which path leads there (`graph.py show`), and answer only as far as ✅ nodes support.
- **Hold competing explanations open.** When several mechanisms could explain the observation, add an entry to `open-questions.md`: the candidates, which nodes each depends on, and a cheap self-test the learner can do to tell them apart. Don't pick a winner before the evidence does.
- **New nodes and corrections** the question reveals go into the graph right away.

### F. Simplifications and corrections

Teaching a simplified model first is the point of the approach; letting the simplification pass as the full truth is the danger.

- Every simplification in the learner's model is written in that node's body, with the node that will correct it.
- When a later node corrects an earlier ✅ node, edit the earlier node's summary in place and set a `caveat` stating the scope in which the old ✅ still holds (`graph.py set ID mastered --caveat "…"`). If the learner actually held the old belief, add it to `debts.md` as a misconception to retest.
- If you find you over-claimed earlier, say so plainly and fix the record. The learner is building on it.

### G. Ending a session

Update the files with targeted edits (never regenerate a file from memory — files drift when rewritten):

- node summaries and `graph.py set` for every node touched; new nodes via `add`
- `debts.md` (forward references, misconceptions to retest, skipped retests, flawed exercises), `open-questions.md`, `glossary.md`, `sources.md` as needed
- run `graph.py sync` — it validates and regenerates `STATE.md`, which is what the next session starts from

If `sync` reports errors, fix them before ending; the next session must start from a consistent graph.

### H. Changing the goal

Learners revise their goal, most often its altitude ("I don't need every detail after all, just enough to follow the project") or its object ("teach me the field's knowledge, not our project's plans" — see "Pin the object" in section A). Nodes built for the old goal are usually still true, just not what the learner needs now. Keep them; don't retire them.

1. Rewrite `goals.md` for the new goal. Move what the old goal covered and the new one doesn't into the non-goals, and name the groups that hold it, so a later session knows where to resume a deep dive.
2. Build the new layer as **new groups** (`graph.py add` with `--group-title`). Don't retitle old nodes to fit: their IDs, statuses and summaries describe what was built or taught under the old goal.
3. In `topic.yaml`, set `[track] main` to the groups that serve the new goal — the new groups, plus any old groups whose content still fits — and replace the goals with the new targets. The remaining old groups drop to side groups: `next` stops recommending them but can still reach them, and any ✅ in them still counts.
4. Record in a comment in `topic.yaml` why the old groups are off the main track, then `sync`.

Retire a node only when it is wrong or duplicated, never just because it is out of the current goal's scope — a retired ID can't be used again, and a deep dive later would have to rebuild it.

### I. Retrospective: the outer loop

Sections A–H run the inner loop: diagnose, teach, record. They never ask whether the goal, the route or the teaching style still serve the learner. Left alone, that question surfaces only when the learner is already frustrated. A retro asks it on a schedule.

**When.** `next` suggests one when:
- the learner comes back after a long gap;
- many status changes have happened since the last retro;
- several ✅ nodes were demoted (hollow mastery);
- a whole group has just been finished.

Also hold one whenever the learner sounds stuck or unmotivated, whatever the script says.

**How.** Keep it to about five minutes, one or two questions at a time, as a conversation:
1. **Meaning.** Read each goal's `question` aloud. Is it still what the learner cares about? Answer as much of it as the ✅ nodes now allow; this shows progress in the learner's terms.
2. **Method.** What felt off in recent lessons: pace, question difficulty, too much or too little big picture, example quality?
3. **Route.** Given 1 and 2, does the next stretch of the route still make sense? Which group needs its map node next?

**Record.**
- Append a dated `## YYYY-MM-DD` entry to `retro.md`: what was said, and what changed.
- Apply each change at the right layer (see "Where things live"): goal and route → `goals.md` / `topic.yaml`; topic rule → `rules.md`; teaching method → the skills; learner-wide preference → workspace `AGENTS.md`.
- Promote any auto-memories collected since the last retro, and delete them once promoted.

### J. Review: ✅ fades

A ✅ records that the learner showed understanding *on that day*. Weeks later, a node that many others build on may have faded, and lessons standing on it start to wobble. `next` names the ✅ node most due for review: verified at least `review_after_days` ago, with dependents, the most depended-on first.

- Review costs one question, asked at the start of a lesson: an isomorphic question from that node's top layer, written from its summary.
- Right → `set ID mastered` again, which refreshes `verified`.
- Wrong → `set ID taught`. Re-teach briefly (usually one example and two questions), then set it again. The demotion warning lists the ✅ descendants to re-check.
- Never review more than one node per lesson unless the learner asks. Review is upkeep, not the lesson.

## Writing node summaries

The summary in a node's body is the canonical model. The next session must teach consistently with what was taught, so it states the claim as taught, with the exact terms and the attribution boundaries. It is the learner's model, not an encyclopedia entry: compact, precise, flagged where simplified.

- **Current state, not history.** No "session 3: we covered…" logs (`log.jsonl` keeps the machine record). When something changed, the useful residue is the corrected statement, the scope of the old one, and — if the learner held it — a pitfall line in the node body (plus a `debts.md` retest item until it is retested).
- **Write in the learner's language,** with standard terms (usually English for technical fields) alongside.
- **Include**: the claim; why it exists (motivation, in a line); the picture or table used, kept in the body so the next session reuses it; terms introduced; attribution boundaries and known simplifications (⚠️, naming the node that corrects them); for `taught` nodes, where the lesson stopped.
- **Keep it lean as it grows.** Long-settled ✅ summaries can compress to a line or two. Resolved open questions shrink to their conclusion. Paid debts are deleted.
- Group-level material (a shared caveat, a preview of a group's target answer marked as *not yet learned*) goes in `_group.md`, not in any node.
